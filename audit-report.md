## 1. STREAMING: reader deadlock, buffers compartilhados, stuck no Windows

| Problema | Onde (arquivo:linha) | O que está mal | O que deveria ser | Prioridade | Evidência |
|---|---|---|---|---|---|
| ReadableStream sem backpressure no terminal stream | `src/app/api/terminal/route.ts:38-61` | O `ReadableStream` inscreve-se nos chunks do terminal via `s.subscribe()` mas não trata backpressure. Se o cliente ler devagar, os chunks se acumulam no `terminal.ts` `chunks` array (máx. 200k chars) e o `push()` continua enviando para todos os ouvintes sem filtragem por taxa de consumo. | Implementar controle de fluxo: ou limitar a taxa de envio, ou descartar chunks antigos quando o stream consumidor não está acompanhando, ou usar `pipeThrough` com backpressure. | MED | Line 38-42: `const stream = new ReadableStream({ start(controller) { ... send('chunk', c) ... } })` — no `if (!open)` check antes de enfileirar, e o `terminal.ts push()` (line 113-126) envia para todos os listeners sem considerar se eles conseguem processar. |
| Ping interval após desconexão do cliente | `src/app/api/terminal/route.ts:50` | `setInterval(() => send('ping', { at: Date.now() }), 20_000)` pode disparar após o cliente desconectar. O `stop()` sets `open = false`, mas há uma janela de corrida entre o intervalo disparar e `open` ser verificado no `send`. | Cancelar o intervalo imediatamente na função `stop()`, ou verificar `open` antes de marcar o ping. | ALT | Line 50: `const ping = setInterval(() => send('ping', { at: Date.now() }), 20_000)` — `stop()` seta `open = false` (line 54), mas se o intervalo disparar entre o check e o enqueue, `controller.enqueue` pode falhar silenciosamente. |
| Timer + cancel race em execute stream | `src/app/api/execute/route.ts:53,76-78` | O `setTimeout` mata o processo após 120s e o `cancel()` (chamado em desconexão do cliente) também mata. Se ambos dispararem próximo no tempo, há risco de double-kill ou estado inconsistente do processo. | Usar flag atômica ou promise de uma só vez para garantir que apenas uma das duas rotinas terminate o processo. | ALT | Line 53: `const timer = setTimeout(() => { if (proc.pid) killTree(proc.pid) }, STREAM_TIMEOUT_MS)` <br> Line 76-78: `cancel() { killChild() }` — chamado quando o cliente desconecta. |
| Pipe deadlock child process → Node stdout/stderr | `src/lib/terminal.ts:85-90` / `src/app/api/execute/route.ts:45-50` | O child process tem `stdio: ['pipe', 'pipe', 'pipe']`. Se o child escrever muito e o Node não ler rápido o bastante, os buffers do OS enchem e o child bloqueia (deadlock clássico de pipe). O `MAX_BUFFER_CHARS = 200k` em `terminal.ts` só discards chunks antigos após o fato, não impede o bloqueio do child em tempo real. | Usar `maxBuffer` nos listeners de `data`, ou migrar para `pipevia`/`pino` com backpressure real, ou limitar o output do child antes de escrever nos pipes. | MED | `terminal.ts` line 88: `stdio: ['pipe', 'pipe', 'pipe']` — no `maxBuffer` configurado nos event listeners. <br> `execute/route.ts` line 150-154: `proc.stdout.on('data', ...)` não tem backpressure — Node chama o handler para cada evento `data` independentemente de o consumidor estar lendo. |

## 4. terminal: kill, histórico, histórico(after)

| Problema | Onde (arquivo:linha) | O que está mal | O que deveria ser | Prioridade | Evidência |
|---|---|---|---|---|---|
| `interrupt()` pode não interromper shell ocupado sem PTY | `src/lib/terminal.ts:162-185` | A documentação diz que escrever `\x03` no stdin não funciona sem PTY no Windows — o Ctrl+C é evento de console, não byte. O `interrupt()` mata processos filhos via `childrenOf` + `killTree`, mas se não houver programas externos rodando (apenas o shell ocupado, ex: `Start-Sleep`), retorna 0 e mostra warning. O shell continua bloqueado. | Adicionar fallback para fechar a sessão inteira se `interrupt()` detectar que nenhum processo filho foi encontrado mas o shell ainda estiver alive há mais de X segundos. | ALT | `terminal.ts` line 162-185: `async interrupt()` — line 168-170: `if (!filhos.length) { warning; return 0 }` — shell ocupado permanece rodando. |
| `interrupt()` loop de wait pode bloquear sessão | `src/lib/terminal.ts:178-183` | O while loop `Date.now() < limite` espera filhos sumirem com pauses de 100ms, limite de 5s. Em carga alta, o `killTree` pode levar mais tempo e o loop terminar antes de os processos realmente sumirem, deixando órfãos. | Usar polling com `childrenOf` a cada 100ms e timeout maior (ex: 10s), ou retornar a promessa apenas quando a confirmação for real. | MED | `terminal.ts` line 178-183: `while (Date.now() < limite) { if (!(await childrenOf(pid)).length) break; await new Promise(r => setTimeout(r, 100)) }` |
| `history(after)` não documenta ID reinicialização | `src/lib/terminal.ts:128-131` | O método `history(after = 0)` retorna chunks com `id > after`. Se a sessão for reaberta, os IDs reiniciam (são `uuidv4()` gerados na criação), então `after` de uma sessão antiga não tem significado across sessões. | Documentar que `history` só funciona dentro da mesma sessão viva, ou incluir timestamps para cross-session queries. | BAI | `terminal.ts` line 129-131: `history(after = 0): TerminalChunk[] { return after ? this.chunks.filter(c => c.id > after) : [...this.chunks] }` — IDs são por-session. |
| `killTree` no Windows depende de `taskkill` que pode falhar silenciosamente | `src/lib/shell.ts:62-72` | No Windows, `killTree` usa `spawn('taskkill', ['/pid', String(pid), '/T', '/F'])`. Se o processo já terminou ou não tem permissão, `p.on('error')` resolve `false` e ninguém sabe. No Linux, `process.kill(-pid, 'SIGKILL')` pode matar o grupo inteiro inclusive o conhost (o que é indesejado). | Adicionar verificação de código de retorno mais robusta e log de erro quando `taskkill` retorna códigos não-0. | ALT | `shell.ts` line 62-72: `export function killTree(pid): Promise<boolean>` — retorna `false` em error, mas caller não sempre verifica. |

## 5. paths: path handling, pipes/reader deadlock

| Problema | Onde (arquivo:linha) | O que está mal | O que deveria ser | Prioridade | Evidência |
|---|---|---|---|---|---|
| `resolveInside` pode permitir escapes via junctions no Windows | `src/lib/agents/fsutil.ts:59-91` | A função usa `path.resolve`, `path.relative` e `fs.realpathSync` para detectar escapes, mas junctions (ponto de montagem do Windows) podem fazer `existsSync` retornar `true` para um link que aponta para fora do projeto, enquanto `realpath` revela o destino fora. O código tem tries/catches para isso, mas caminhos complexos podem passar despercebidos. | Testar com caminhos que usam junctions/soft-links e garantir que `realpathSync` seja chamado em cada ancestor antes de aceitar o path. | MED | `fsutil.ts` line 59-91: `resolveInside` — comments em line 62-63 já admitem essa limitação: "On Windows, some test runners/filesystems do not permit creating symlinks; use lstat-based traversal whenever the path can actually be inspected." |
| `safePath` no fs/route usa `startsWith('..')` que falha com paths codificados | `src/app/api/fs/route.ts:11-16` | `safePath` faz `path.relative(ROOT, target)` e checa `relative.startsWith('..')`. Se o path usar `..` codificado (ex: `%2E%2E%2F`), o `path.relative` normaliza mas casos com combinações estranhas de barras podem escapar. | Adicionar decodificação URI antes do resolve, ou usar `path.normalize` explícito. | BAI | `fs/route.ts` line 11-16: `const target = path.resolve(ROOT, input || '.'); const relative = path.relative(ROOT, target);` — sem `decodeURIComponent` prévio. |
| `removeDir` usa retries fixos que podem não ser suficientes no Windows | `src/lib/agents/fsutil.ts:138-141` | O `removeDir` tenta 10 vezes com delay 300ms (total 3s). Alguns antivírus ou bloqueios de sistema podem segurar arquivos por mais tempo. O error do `fs.rmSync` não é propagado — o caller só vê se o dir foi removido ou não. | Tornar o número de retries e o delay configuráveis, ou logar warnings quando falhar após todos os retries. | MED | `fsutil.ts` line 139-141: `fs.rmSync(dir, { recursive: true, force: true, maxRetries: 10, retryDelay: 300 })` — sem log de falha. |
| Pipes de terminal podem deadlock se output for grande | `src/lib/terminal.ts:85-90` / `src/app/api/execute/route.ts:45-50` | Igual ao item 1: pipes `['pipe', 'pipe', 'pipe']` sem backpressure. O child process pode bloquear escrevendo mais do que o Node lê. O `windowsHide: true` também pode mascarar errors de pipe entupimento. | Adicionar `maxBuffer` nos event listeners ou migrar para streams com backpressure. | MED | `terminal.ts` line 91-92: `this.proc.stdout.on('data', (d: Buffer) => ...)` — sem controle de buffer. <br> `execute/route.ts` line 150-154: mesma estrutura, mas com `maxOutput` no level de `runWithShell`. |
| `canonical` em `safeRealPath` depende de `fs.realpathSync` existir | `src/app/api/fs/route.ts:35-40` | A função `canonical` chama `fs.realpathSync.native(existing)` que pode lanzar se o path não existir ou houver permissões restritas. O try/catch ao redor do GET handler (line 84-86) captura o error, mas paths borderline podem causar 400 errors inesperados. | Garantir que `canonical` retorne o ROOT em caso de erro, em vez de lanzar. | BAI | `fs/route.ts` line 35-40: `function safeRealPath` — `fs.realpathSync.native(ROOT)` pode falhar se ROOT for removido estranhamente. |
